## Phase 4 — manager rulings (binding, but not assumed correct)

### R1 — build type: **keep `ament_python`**. (Overrides the issue's stated lean.)

The issue says *"Lean: convert to ament_cmake."* I am ruling the other way, and
this is the one ruling most worth attacking.

Why the lean loses on this repo's evidence (`context.md` §1a–1f):
1. **PRs 2–7 would have to remember a registration step.** Under `ament_python`,
   `pytest.ini`'s `testpaths = test` auto-discovers any new test file. Under
   `ament_cmake`, every new test needs an explicit `ament_add_pytest_test()`
   line in `CMakeLists.txt`; forget it and the test *silently never runs*. This
   PR's whole stated purpose is to be "the harness PRs 2–7 extend" — a harness
   whose extension step can be silently skipped is the wrong harness.
2. **It would blind the test-integrity guard.** `is_linter_case` /
   `LINTER_TEST_NAMES` (`check_test_integrity.py:86-90,325-336`) match
   `test_flake8`-style names; `ament_lint_auto`'s hooks emit bare `flake8` /
   `copyright` / `pep257`. Those would be miscounted as *real* tests, inflating
   the baseline and partly defeating the `_STATUS_NO_REAL_TESTS` check. Fixing
   it means editing shared tooling outside this package's owned paths, plus new
   tests in `scripts/tests/`.
3. **An unverified plugin risk.** `ament_add_pytest_test` does not pass
   `-p no:launch_testing -p no:launch_ros`, and ctest's working directory is the
   *build* dir, not the source dir where `pytest.ini` lives. The RoboStack
   plugin incompatibility that every existing `pytest.ini` documents could
   resurface.
4. **It would be the repo's only `ament_cmake` package** — eight siblings are
   `ament_python`, and there is no in-repo `CMakeLists.txt` to crib from.

What the lean actually buys is convention: `ament_cmake` is the common build
type for description packages upstream. But the concrete thing it is wanted for
here — installing `share/<pkg>/{urdf,meshes}` — `ament_python` does equally well
via `data_files` (R2). Nothing in PR1 needs CMake. If PR7's MJCF work turns out
to need a genuine build step, converting *then*, with a concrete driver, is
cheaper than converting *now* on a hunch.

Corroborating signal: R1 **dissolves** open questions 1 and 2 rather than
answering them — no `LINTER_TEST_NAMES` edit, no `ament_add_pytest_test`
pytest.ini risk. `scripts/check_test_integrity.py` is **not** to be touched by
this PR.

### R2 — layout and install wiring
Source: `src/robot_description/urdf/{robot.urdf.xacro,base.xacro,column.xacro,arm.xacro}`
and `src/robot_description/meshes/`. Install to `share/robot_description/urdf`
and `share/robot_description/meshes` via `data_files` in `setup.py`, using
**globs** (`glob('urdf/*')`, `glob('meshes/*')`) — **not** a hand-maintained file
list, for the same reason as R1: a PR2–PR7 author must not have to remember to
register a new `.xacro` for it to be installed.

`meshes/` must be non-empty or git won't track it and the install dir won't
exist. Ship `meshes/README.md` (a real note that geometry lands in PR2+), not a
`.gitkeep` — `glob()` skips dotfiles, so a `.gitkeep` would *not* be installed
and the directory would silently not exist in the install space.

### R3 — the tests run against the **installed** share dir, with no fallback
Resolve the xacro via
`ament_index_python.packages.get_package_share_directory('robot_description')`,
**not** a path relative to `__file__`. This makes the R2 install wiring part of
what the gate actually verifies. **A fallback to the source tree is forbidden** —
it would mask exactly the install-wiring break we want caught.

inside the suite. If it nonetheless proves unreliable, **escalate to the manager**
— do not add a fallback.

### R4 — three gates, three tools, matching the brief's three bullets
- **expand** — invoke the **`xacro` CLI** via `subprocess`, assert `rc == 0`.
  CLI over `xacro.process_file` because it is what launch files actually run,
  and because rc + captured stderr is a legible failure for PRs 2–7.
- **parse** — invoke the **`check_urdf` CLI** on the expanded output, assert
  `rc == 0`. Execute-verified (Phase 2) to return 255 on *both* malformed XML
  and semantic errors, so it is a real gate.
- **link set** — `urdf_parser_py.urdf.URDF.from_xml_string(...)`, assert
  `{l.name for l in robot.links} == {'base_link'}`. A real parse, not an XPath
  scrape.

  **Corrected after round-1 red-team (was wrong as originally written).** This
  ruling claimed the link-set assert was load-bearing because it catches a
  degenerate zero-link expansion "regardless of how `check_urdf` treats it".
  That is **false**: a zero-link expansion fails `check_urdf` too (VERIFIED).
  The set assert's genuine unique catch is a link that is **renamed or silently
  dropped while the model stays valid** (`base_link` → `base`: 1 failed, 4
  passed) — which is the likelier PR2–PR7 regression anyway, since every
  consumer names links. The three-tool design stands; my stated reason for it
  did not. Same false sentence was corrected in `test_description.py`'s
  docstring and in D27 (red-team N1).

Write these as **separate test functions** (plus one asserting both
`share/robot_description/urdf` and `.../meshes` exist), so PRs 2–7 get a precise
signal rather than one fused pass/fail. A module-scoped fixture that expands once
is fine.
