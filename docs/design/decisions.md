# Robot Project — Decisions Log

Append-only record of settled decisions with rationale. Newest at the bottom. Reversing a decision = add a new dated entry that supersedes the old one (don't edit history).

## 2026-08-09 — Initial architecture + stack (scoping session)

- **D1 — Physical form:** 4-wheel base + extendable vertical column + 2 arms (elbow + claw) + head (RGB-D cam + mic). Wheels over legs; exactly 2 arms (not >2); standard camera placement (not 360). *Rationale:* cost/stability, field convergence, off-the-shelf VLA compatibility. The extendable lift is the deliberate differentiator vs. fixed-height DIY platforms.
- **D2 — Control altitude: hybrid.** Skill/pose commands are the default; raw per-DoF joints kept only as a debug/teleop escape hatch. *Rationale:* the LLM must not do IK; relative per-DoF commands drift and can't verify contact.
- **D3 — Perception output:** structured scene JSON with grounded 3D coordinates, not prose captions. Depth camera required. *Rationale:* manipulation needs metric object poses.
- **D4 — Closed loop + safety:** every skill returns status + a fresh observation (event-driven). A safety/clamp layer (joint limits, collision checks, gripper force limits, e-stop) is mandatory from day one.
- **D5 — Framework: ROS 2 Jazzy.** *Rationale:* Nav2 (SLAM/nav) + MoveIt 2 (collision-aware planning) are exactly this robot class and hard to replicate; ROS 2 is headless-native. Python/LeRobot-native path rejected as it would mean rebuilding both.
- **D6 — Simulator: MuJoCo** via `mujoco_ros2_control` (Gazebo as fallback). *Rationale:* best contact physics for manipulation, most headless-friendly, officially supported under ros-controls.
- **D7 — Kinematics: MoveIt 2 + TRAC-IK.** IKPy/Pinocchio acceptable for early prototyping.
- **D8 — Visualization: Foxglove Studio** (web, via `foxglove_bridge`) over rviz. *Rationale:* headless development is a stated priority.
- **D9 — Backend abstraction:** Mock → Sim (MuJoCo) → Real behind one `RobotBackend` interface. *Rationale:* develop/test the harness with zero physics, then swap backends without touching brain code.
- **D10 — Isaac Sim + GPU rental: deferred (conditional).** Not a planned phase. *Trigger:* a camera-based learned policy hits a photoreal sim-to-real wall, or a need for NVIDIA GR00T/cuRobo. Plain RL can use MuJoCo MJX first.
- **D11 — Compute:** develop on the Xubuntu laptop (CPU, $0). Raspberry Pi 4 = deployment target only, not a dev/sim box (may be swapped for a Jetson). Rent a GPU hourly only if D10 triggers.
- **D12 — Reuse/fork strategy:** don't fork a monolith. Consume frameworks (MoveIt 2, Nav2, MuJoCo, LeRobot, Foxglove) as dependencies; fork **one** ROS 2 robot reference for description+bringup (evaluate **AhaRobot** first, then the ROS 2 dual-SO-101 project, then **youfork**); reuse `so101_ros2` for the arm-in-ROS 2 layer; **build** the LLM harness (crib Stretch AI). XLeRobot = BOM/mechanics crib only (it's Python/LeRobot + fixed-height + low-spec, not a software fork target). *Rationale:* ~85% of the stack exists; the brain is the novel ~15%. Forking imposes hardware assumptions only at the URDF/driver layer (brain is hardware-agnostic via the skill API); the extendable column is custom regardless. See PROJECT.md "Reuse map / fork strategy."
- **D13 — Repo structure:** one **base repo** holds all glue/IP (brain, skill API, safety, backends, perception, description, bringup, tests); externals come in via **depend / pin (vcstool) / fork (only when patched) / vendor-crib** tiers, never buried in a fork. The **skill API is the seam** between hardware-agnostic brain and swappable drivers/URDF. *Rationale:* keeps IP + licensing clean, upstream updates manageable, hardware layer replaceable. Public push deferred (outbound action). See PROJECT.md "Repository & tooling."
- **D14 — Languages:** **Python (rclpy) primary** for all IP; **C++ (rclcpp)** only later and only for an unavoidable custom `ros2_control` controller or MCU firmware (ESP32/PlatformIO / micro-ROS); XML (URDF/Xacro, MJCF) + YAML + Python launch; **Python 3.12** (Jazzy). *Rationale:* LLM/LeRobot/ML ecosystem is Python; heavy compute lives in compiled deps we invoke; the slow (~1 Hz) brain makes Python safe. Mock harness runs with no C++ toolchain.
- **D15 — Package/env manager:** **pixi + RoboStack (`robostack-jazzy`) primary** — one locked cross-machine env for ROS 2 + Python + native deps; **uv fallback** if using official apt ROS 2 (aligns with Pi apt/Ubuntu deployment), managing only the PyPI layer. **colcon still builds** the ROS packages; don't run both env managers. *Rationale:* reproducibility + headless + laptop/rented-box parity. TODO: verify RoboStack coverage of Nav2 / `foxglove_bridge` / `mujoco_ros2_control`; source-build any gaps inside the pixi env.
- **D16 — System topology / control plane:** three tiers — **Pi OpenClaw bot** (Telegram relay + user prefs) → **laptop robot-agent service** (our harness; warm FastAPI holding ROS/map/models) → **cloud LLM**. **Async task API** (`POST /task` → `task_id`) over WireGuard with status callbacks + cancel; per-task loop = plan → atomic step (**ROS 2 action**) → re-perceive → replan, until done + optional photo. **Guards:** max-steps/timeout/stuck-detection, user stop/cancel mid-step, heartbeat/dead-man on link loss, one-task-at-a-time (`idle→running→done/failed`). **Two memories:** world-state = queried store (day one); user prefs = persistent, prompt-injected (grows). Robot agent ≠ OpenClaw bot. **Backend-agnostic → sim-first** (whole flow testable in MuJoCo before hardware). *Rationale:* async + warm service + guards make it robust for a real home; keeps IP in our harness; end-to-end testable in sim.

## 2026-08-10 — Skill/observation seam ratification (pre-second-package)

Three internal-seam calls from the mock-skill-api run (#17, #18, #20), settled before a second skill package binds. They follow from D1–D16 and interlock: #20 adds a field governed by #18, and #20's force edge is governed by #17.

- **D17 — Physical limits: two layers, two failure modes (closes #17).** Split by *kind* of limit, not by component. **Kinematic/workspace reachability** (target pose out of range, joint stop, self-collision, unreachable) is the **backend's** job: it *refuses* the skill up front and returns a "couldn't run" error (`unreachable`/fault) before motion. **Dynamic safety** (joint-limit clamp, collision avoidance during motion, gripper force limits, e-stop) is the **safety/clamp layer** (D4): it sits between brain-issued skills and the backend and *clamps or aborts* in-flight, returning a safety event. Rule of thumb: *"can't be done" = backend refusal; "unsafe to continue" = safety-layer clamp/abort.* The brain treats both as closed-loop signals, not exceptions to route around. *Rationale:* keeps `robot_safety` backend-agnostic (same clamps regardless of Mock/Sim/Real) while each backend owns only its own reachability; matches D2 (LLM never does IK) and D4 (mandatory safety layer from day one).

- **D18 — Wire-format compatibility: version-stamped single source, atomic in-repo updates, golden-fixture guard (closes #18).** One schema definition for `Observation` / `SkillResult` / skill signatures as typed models in a single package, carrying an explicit `SCHEMA_VERSION`. Because every consumer lives in the one base repo (D13), a breaking change updates *all* binders in the *same* PR — no multi-version support, no deprecation windows (zero external consumers yet). **Compat rule:** additive optional field = non-breaking; remove / rename / retype = version bump + update all binders atomically. **Enforcement:** a golden-fixture schema test that fails if a field is dropped or retyped without a `SCHEMA_VERSION` bump (fits the test-integrity guard from #24). *Rationale:* the payoff of not vendoring (D13) is atomic cross-consumer edits; spend the complexity budget on a guard, not a deprecation machine.

- **D19 — `close_gripper` on an empty gripper: success + `grasped` flag, not an error (closes #20).** Add an additive `grasped: bool` (with aperture / contact-force detail) to `SkillResult`/`Observation`. `close_gripper` on nothing is a **successful** skill that reports `grasped=false`; the brain learns "did I get it?" from that flag in the closed loop (D4), not from a raised exception. Same idempotent-report semantics for `open_gripper` on an already-open gripper. Errors stay reserved for "couldn't run" (fault, unreachable, e-stop); **over-force while closing** is a *safety event* on D17's clamp/abort path, a separate concern. *Rationale:* grasp success is normal control-loop information, not a failure; the new `grasped` field is exactly an additive, non-breaking change under D18.

## 2026-08-11 — Run-end notification + merge authority (ops plumbing)

- **D20 — Push-primary run-end notification with a cron backstop.** A dispatched run's completion wakes Sisyphus by **push** (`scripts/pi/watch-run.sh`, ~15s) rather than by poll; the 15-min `sisyphus-pr-check-backstop` cron is demoted to a pure safety net for pushes that never land (Pi reboot, dead watcher, dropped SSH). **Completion is signaled by the `EXIT=<code>` marker in the run log, not tmux-session death** — the launcher leaves an idle `exec bash` shell, so the session outlives the run and session-death would fire early (hard kills, which never write the marker, still fall back to session-gone). **Sisyphus is the sole merger:** the cron only wakes it, and managers/operational agents stop at an open, green PR. The merge policy lives in **one** canonical file, `.claude/commands/run-merge-eval.md`, referenced by both triggers. *Rationale:* two runtime copies of the policy (cron prompt + wake message) drifted; a single in-repo doc plus in-repo dispatch scripts (`scripts/pi/`) make the repo the source of truth for the control plane, matching D13.

## 2026-08-11 — Brain = the OpenClaw agent itself (architecture pivot; supersedes the brain location in D16)

- **D21 — The robot's brain IS a dedicated OpenClaw Telegram agent, not a custom harness (supersedes the brain-location half of D16).** Jaime talks to an OpenClaw agent over Telegram; that agent *is* the planner. Its **system prompt** carries the skill API (names/args/units/limits) + observation format + safety envelope + 2–3 worked examples. It plans by **calling the robot's skills as MCP tools** (`robot_mcp`) and reads each tool's structured `SkillResult` + `Observation` back — **OpenClaw's native tool-call loop IS the perceive → decide → act → re-perceive loop** (D4), so there is **no custom planner loop and no tag/tool-call parser** (the `<grasp mug_1>` text format of D2 is obsoleted by native tool-calling), and OpenClaw's **native memory** serves the user-preference store.
  - **Laptop is reduced to the robot-side service:** the `robot_mcp` tool server + skill impls + safety/clamp layer (D17) + perception + ROS 2 connection / map / models / sim, all behind the one **skill-API seam** (D13). There is **no custom FastAPI "brain."**
  - **Determinism boundary:** everything *below* the tool call is deterministic Python + physics; the **only** stochastic element is the brain's choice of tool + args. The **sole additional neural model** is perception (Grounding DINO / SAM / depth), and only on the real/detector path — Mock and MuJoCo-ground-truth-pose modes are model-free. **No second LLM.**
  - **Safety, e-stop, and hard guards are enforced server-side, below the tool boundary — never by the LLM** (D4/D17).
  - **Deferred to contingencies (the former D16 build items):** the custom `robot_brain` planner loop and the FastAPI task-service. Built **only if OpenClaw proves lacking**, on three concrete triggers: (i) heavy observations bloating LLM context, (ii) headless autonomy needed without a chat round-trip, (iii) a control cadence tighter than chat-paced. Given the "operational, not reactive" target, chat-paced is expected to suffice.
  - *Rationale:* collapses "build a brain" into "expose good skills as tools + write a good operating prompt" — a far smaller, more tractable surface; matches what OpenClaw already is; `robot_mcp` (#37/#38) already points this way. **What remains "our IP" narrows to:** the skill API + MCP surface, the safety layer, perception → scene-JSON, the robot description (URDF/MJCF, incl. the custom extendable column), and the prompt/tool design that makes an LLM drive it well.

- **D22 — Scope: a slow, low-cost chore robot, explicitly NOT competing with the frontier.** The target is a robot that *eventually gets some chores done* on a small budget — not SOTA dexterity, not a research win. **Favor reuse + classical/scripted skills first:** MoveIt pick-and-place of *rigid* objects + Nav2 driving + the LLM planner already covers "drive over, pick that up, put it there, tidy, load the dishwasher" with **no learned policies at all**. **Learned skills** (imitation learning via LeRobot / VLA, teleop data collection) are pulled in **only** for the specific chores classical methods can't do. *Rationale:* keeps cost ($0 laptop compute, ~$1k open hardware, no GPU until genuinely forced per D10) and difficulty down; the genuinely-custom hard parts (the extendable column, robust fragile-object grasping) are the differentiators and the real risks — not the whole robot.

## 2026-08-12 — World state moves out of the code and onto the disk

- **D23 — World state is a JSON-file store (`robot_world`), seed and live state kept separate, written atomically (closes #54).** The map (named locations) and the object registry (id, label, pose, graspable, held-by) live in a pure-Python **`WorldStore`**, not in a Python literal inside the Mock backend. A **`FileWorldStore`** persists that scene as **JSON** (stdlib only — the file is machine-written, so YAML buys nothing and costs a parser), so the world **survives an MCP process restart**. Two files, **one document schema**: a **read-only seed** shipped inside `robot_world` and a **live-state file** the robot writes; `reset()` re-reads the *seed file* and rewrites the live file from it, so the first mutation can never destroy ground truth. Every write is **atomic** — temp file in the target's own directory, then `os.replace`, temp removed on any failure — and **one skill is one write** (a store `batch()`), so a crash can never leave a half world. Four boundaries make it the layer that survives the MuJoCo swap:
  - **The store holds the scene, the backend holds the robot.** Locations and objects are the store's; proprioception (base pose, column height, gripper posture) and all reach arithmetic stay in the backend. Mock-specific arm offsets would otherwise be baked into a file the Sim backend inherits.
  - **The world file never describes the robot's body.** `RobotModel` (shoulder offsets, reach, column travel) is hardware description and stays in code, later coming from the URDF/MJCF.
  - **A restart is a power cycle.** The robot comes up at the scene's start posture with empty grippers, so any object the file still records as `held_by` is released *where it lies* (its persisted pose is kept). Persisting `held_by` without gripper state would otherwise make the first `get_observation()` raise, since `Observation` enforces that the two views agree — and it makes a crash mid-skill recover cleanly either way.
  - **Persistence is opt-in.** `MockBackend()` and `python -m robot_mcp` with no options **never write a file** — the only file either opens is `robot_world`'s read-only shipped seed; a live world is asked for explicitly (`store=FileWorldStore(path)`, `--world-state PATH` / `$ROBOT_WORLD_STATE`, `--world-seed` / `$ROBOT_WORLD_SEED`). Defaulting persistence on would make the Mock's documented determinism false and would silently break the existing spawned-server test on its second run.

  The document carries its **own** `world_schema_version`, a separate counter from D18's `SCHEMA_VERSION`: this is an on-disk format between the robot and its own past self, not the brain↔robot wire format, and the two must be free to move independently. Parsing reuses `robot_skills.serialization` and is strict in the same way (unknown key, missing key, wrong type, foreign version → loud error). A **missing** live file is seeded; a **corrupt** one is never silently repaired (that would destroy the only evidence); a missing or corrupt **seed** is always a hard error. Accepted gaps, recorded rather than assumed away: no `fsync` (atomic against a crashed process, not a power cut), no cross-process lock (single robot-side service, one task at a time — D16/D21), and no location add/remove API yet. *Rationale:* the roadmap's step 3 and D16's "world-state = a queried store, needed day one"; the scene stops being something only a code edit can change, and perception (invariant 4) and the MuJoCo swap both get a data layer to write into instead of a frozen literal.

## 2026-08-12 — The deploy path discovers itself, and the gate boots it

- **D24 — The launch path discovers the workspace; hand-maintained package lists on the deploy path are banned, and the gate boots the server through the same launcher the deployment uses (closes #56).** #55 shipped a break no check could see: `robot_mcp/server.py` began importing `robot_world` at module load while the launch command's hand-written `PYTHONPATH=…` still listed four packages. `pixi run test` stayed green — colcon builds every package from its manifest graph and never reads a launch string — and the deployed server died with `ModuleNotFoundError`, leaving the brain with no tools. The rule this settles is structural rather than procedural, because "remember to update the list" is what already failed:
  - **One source of truth for "what is a package": `src/*/package.xml`.** `scripts/robot-mcp-launch.sh` builds `PYTHONPATH` from the manifests it finds and `exec`s `python -m robot_mcp`; the OpenClaw fragment, the READMEs and any MCP client config name **the launcher**, never packages. A package added tomorrow is on the path with no edit anywhere. There is no allowlist and no "only the ones the server imports" filter — a filter is the banned list wearing a different hat — and discovering **zero** packages is a loud non-zero failure, never an empty path to launch with.
  - **The environment and the path are separate jobs.** `pixi run` supplies the environment; the launcher supplies the path, does not shell out to `pixi` and does not sniff whether it is inside one. That separation is what lets the gate execute the identical file the Pi executes instead of a re-implementation of it, and it is why the launcher resolves its repo root lexically (no `readlink -f`): the path it was invoked by is the checkout it was asked to launch.
  - **The gate boots the deployed thing.** `scripts/tests/test_boot_smoke.py` runs that launcher in a child with **`PYTHONPATH` stripped** and speaks a real MCP `initialize` to it, so "green" means "the server starts the way it is deployed". The stripping is load-bearing, not hygiene: hand the child the test runner's own `sys.path` — which is exactly what `mcp_fixtures.clean_environment()` does — and the check passes with discovery completely broken. It is held honest by its own inverse: the same launch with `robot_world` removed from the source tree must fail, and does.
  - **A manual step the gate cannot see is the bug class, not the instance.** Anything hand-typed on a path to production is a second, unsynced source of truth; the remedy is to derive it or to make the gate run it. The same reading covers provisioning: `pixi run test` `depends-on` `scripts/check_provisioning.py`, which stops the run in seconds naming the condition, the path and the one command (`pixi run install-openclaw`), instead of leaving six `robot_brain` failures at the end of a colcon run to be decoded.
  - **Accepted gaps, recorded rather than assumed away.** The gate boots the launcher *directly, already inside pixi* (correctly — the launcher must not know about pixi), so the wrapper around it is **not** executed by any test: the `ssh -T <alias>` hop, the two absolute paths and the `pixi run --frozen --manifest-path` prefix are still hand-typed per deployment. Of that wrapper, the login shell is now *checked* on the laptop rather than assumed — `env -i HOME=$HOME USER=$USER bash -c 'command -v pixi'` finds nothing while the same command with `-lc` resolves `pixi`, so `-lc` is load-bearing, not habit — and what remains unexercised is the `ssh` hop itself and the **Pi's** login shell, which only the Pi can run. What is asserted in their place is the *shape* — that the flattened remote command re-parses into an argv that reaches the launcher (`ssh` joins its arguments with spaces and never re-quotes, which is how the first version of this fragment shipped a command that ran a bare `exec`, started nothing and exited 0), and that the manifest path and the launcher path name one checkout. Everything past that boundary is checked by hand against the README's probe.

  *Rationale:* the failure was not that someone forgot a package — it is that the deploy path was a string only a human ever executed, so the cheapest possible correctness check (starting the thing) was never run. Discovery removes the list; the boot-smoke removes the "never run". No implementation module changed for this: the edits inside `src/` are the OpenClaw fragment's launch string, `test_openclaw_config.py` (the hand-list test inverted, the launch-command tests rewritten around the launcher and the flattened-command assertions added), and the two READMEs that documented the old command — the seam (`RobotBackend` / `Observation` / `SkillResult` / `SCHEMA_VERSION`) and invariants 1–5 are untouched, because this decision is about how the system is launched and tested, not about what it does.

## 2026-08-12 — The reviewer gets a shell

- **D25 — "Read-only" for the red-team means read-only *to the worktree*, not "no shell"; the reviewer runs the code and labels findings VERIFIED / UNVERIFIED.** `.claude/agents/red-team.md` now grants `Bash` alongside `Read, Grep, Glob, Write`. The tool grant contradicted the instruction: `run-feature.md` step 6 already tells the reviewer to *"disprove that claim empirically — run the code, don't reason about it"*, while the agent had no way to execute anything, so it simulated the code in its head and shipped findings marked "UNEXECUTED" that someone downstream — with less context than the reviewer — then confirmed by hand (the #56/#57 run: both a claimed launch-command bug and an unratcheted-baseline claim needed manual checking). The contract is now three clauses: **Bash is for verification only** (run the suite, start the server, reproduce the scenario) — the reviewer still never edits source or tests, and its only Write is its own `red_team.md`; **every finding is labeled VERIFIED (command + output) or UNVERIFIED (why not)**, so the manager can tell evidence from argument; and **the tree is left exactly as found** — a perturbation experiment (delete a package to prove a guard fires) runs on a `cp -r` copy outside the worktree, never in place, confirmed with `git status`. Build artifacts (`build/`, `install/`, `log/`, `.dev/`) are gitignored and expected. *Rationale:* an unexecuted finding is a hypothesis, and the cheapest place to test it is the agent that formed it; withholding the shell did not protect the worktree (an explicit no-edit rule does that), it only moved verification to where it costs more.

## 2026-08-12 — Hardware architecture: commit to the LeRobot/Feetech lineage (supersedes the base + lift specifics of D1)

- **D26 — Every actuated joint lives on one Feetech STS3215 / LeRobot bus; base, column, and arms are all cribbed from the LeRobot substrate rather than authored (tweaks D1's "4-wheel base + extendable column + 2 elbow-claw arms").** The governing decision is the *single servo ecosystem*, not any one component: arms **and** the column run the same Feetech STS3215 servo, so the whole robot is one URDF actuator model, one MJCF, one bus, and forks an existing simulator instead of authoring one. The three component picks follow from it:
  - **Arms — 2× SO-101 (Feetech STS3215), kept.** ~$130 DIY BOM / ~$200–250 kit each; 6-DOF, ~0.25–0.5 kg payload, ~0.4 m reach, plastic. The most cribbable object in the robot: LeRobot-native, URDF + MJCF + ManiSkill/MuJoCo envs already exist, and it is what XLeRobot (our substrate) uses. Authored in the URDF as a **swappable xacro macro** (`prefix`/`side` + mount transform) so a heavier arm can drop in later. **PiPER (Agilex, ~$3,999, 1.5 kg, CAN bus) is penciled in as the real-hardware payload upgrade** — but taking it *breaks the single-bus column* (needs its own controller), so it is deferred to the real-hardware phase, not the sim phase. Rationale for staying SO-101 now: payload is a real-world ceiling (can't lift a full mug/plate), but it is not a *sim* limiter, and sim-first (D9/D16/D21) means the swappable macro costs nothing to defer.
  - **Base — LeKiwi 3-omniwheel holonomic (tweaks D1's 4-wheel base).** A holonomic 3-omniwheel base has a ready-made URDF, is the proven XLeRobot substrate, and is a far easier control problem than a custom 4-wheel base with no reference. The cost is the "4 wheels" aesthetic of D1; the win is the biggest single cribbing gain on the board. Chosen: take the holonomic win.
  - **Column — linear-rail STS3215 lift on the arm bus (Nori-style), not a bespoke belt drive.** One ~600 mm linear rail driven by a single STS3215 on the same Feetech bus as the arms — no second controller board — modeled as **one prismatic joint** in the URDF (this is exactly PR3 of the [[urdf-mjcf-pr-breakdown]], limits 0.00–1.20 per D23's `RobotModel`). This keeps the extendable column (D1's deliberate differentiator) while making it cribbable and single-ecosystem instead of zero-prior-art custom.
  - **Brain / compute — unchanged.** OpenClaw agent on the Pi 4 as planner, laptop as the robot-side MCP/skill service (D11/D16/D21).
  - **Substrate to fork:** **XLeRobot** (~$660: 2× SO-101 + LeKiwi base + IKEA-cart frame; ManiSkill sim + URDFs, <4h build) is the proven base+arms crib — this promotes it from D12's "BOM/mechanics crib only" to the geometric substrate for base+arms, now that the base is holonomic and the ecosystem is unified. **Nori Bot (arXiv 2605.16537, May 2026)** — a ~$947 17-DoF dual-arm mobile manipulator with a 600 mm linear-rail Z-lift on a Feetech bus, a Pi 4 thin client, exposed to an OpenClaw-style agent runtime — is almost this exact stack and is the crib target for the column mechanism and the agent↔hardware seam. **Treat Nori Bot as UNVERIFIED until we read the paper** (flagged, not yet baked into any code).
  - **Gripper — stock SO-101 parallel-jaw (Feetech STS3215, the arm's 6th DOF), kept (Jaime, 2026-08-12).** $0 extra, single-bus, already in the URDF/MJCF, and exactly what the existing skills model (`open_gripper`/`close_gripper`/`move_gripper`/`grasp`/`place` + D19's `grasped` aperture flag). The fingertip is authored as a **swappable link** (same pattern as the swappable arm macro), so **fin-ray / compliant fingers** (official SO-101 "compliant" config; ~$3–5 TPU; free STLs) are a later geometry swap — not a re-model — reserved as the first physical upgrade for fragile-object grip (the D22 risk). **Suction is explicitly deferred**: a pump is not a Feetech servo (needs its own driver → breaks single-bus) and doesn't map onto the aperture/`grasped` skill seam (new skill + observation field), so it is a future *second* end-effector decision, taken only if the flat-dishware chore demands it, not a baseline.
  - **Camera — one head-mounted RGB-D; reserve the link + optical frame now, buy nothing yet (Jaime, 2026-08-12).** D3 + the classical path (D22) need **metric depth** (MoveIt pick-and-place of rigid objects needs true 3D poses), so the real sensor class is **RGB-D**, not a plain webcam — monocular depth (Depth Anything etc.) is not reliable enough for manipulation. But Mock + MuJoCo run on **ground-truth poses** (D21, perception is model-free there), so **no physical camera is needed to build or test the pipeline in sim**. What the URDF gets *now* is a **head camera link + optical frame** mounted on `column_top` (matching XLeRobot's dual-fit head mount, which takes a webcam *or* a RealSense), so the sim can render RGB-D from the correct pose when the real detector path is built and camera→base transforms project detections to metric poses. The MuJoCo sensor is modeled as **active-IR-stereo RGB-D** to match whatever ships. **Real-hardware target penciled: Orbbec Gemini 335 (~$250)** as the head RGB-D; RealSense D435i as the compatibility fallback, OAK-D Lite as the budget floor. **Wrist cameras and a mic are deferred** (Jaime): one head camera only; wrist cams add data-plumbing without a sim need, and audio doesn't serve the chat-paced control plane (D21). Same pattern as the arms — commit the *frame + sensor class* in the URDF now (cheap, reversible), pencil a specific part for the real build, force no purchase before sim proves out.
  - *Rationale:* one servo model collapses the base/column/arm URDF+MJCF+driver work into forking the LeRobot lineage once; it is the biggest "easy to crib for sim and real" lever, worth more than any individual base/lift choice. Supersedes D1's base (4-wheel → 3-omniwheel) and pins the lift mechanism (belt → linear-rail servo); D1's "2 arms + extendable column + head cam" intent is preserved. ## 2026-08-13 — The description package becomes real, and the gate expands the installed copy

- **D27 — `robot_description` stays `ament_python`; the description is one top-level `robot.urdf.xacro` over per-subassembly includes, installed to `share/robot_description/{urdf,meshes}`, and the CI gate expands the *installed* copy (closes #61, PR1 of the URDF/MJCF roadmap).** D23 leaves `RobotModel` (shoulder offsets, reach, column travel) as hardware description that "stays in code, later coming from the URDF/MJCF", and D26 commits the whole robot to "one URDF actuator model, one MJCF, one bus" — this decision is the packaging and gating those two imply, taken before any geometry exists so that PR2–PR7 (base, column, arms, gripper/camera, MJCF) inherit a harness instead of negotiating one. Four clauses:
  - **Build type: `ament_python`, not `ament_cmake`** — against the convention that description packages are `ament_cmake`. What `ament_cmake` is wanted for here is installing `share/<pkg>/{urdf,meshes}`, which `data_files` does equally well; what it would cost is concrete. Under `ament_python`, `pytest.ini`'s `testpaths = test` discovers a new test file automatically; under `ament_cmake`, every new test needs an `ament_add_pytest_test()` line in `CMakeLists.txt`, and a forgotten line is a **silently skipped test** — the wrong property for a package whose stated job is to be the harness five later PRs extend. It would also blind the test ratchet: `check_test_integrity.py`'s `LINTER_TEST_NAMES` matches pytest's `test_flake8`-shaped names, while `ament_lint_auto`'s hooks emit bare `flake8`/`copyright`/`pep257`, which would be miscounted as *real* tests and inflate the floor — fixing that means editing shared tooling to accommodate one package's build type. And it would be the workspace's only `ament_cmake` package, against eight `ament_python` siblings. If PR7's MJCF work turns out to need a genuine build step, converting *then*, with a driver, is cheaper than converting now on convention.
  - **One entry point, empty subassemblies, relative includes.** `urdf/robot.urdf.xacro` (`<robot name="sisyphus">`) is the single file every consumer expands; it declares the root frame `base_link` and includes `base.xacro`, `column.xacro`, `arm.xacro`, which ship genuinely empty for PR2–PR4 to fill. `base_link` lives in the **top level**, not in `base.xacro`: it is the assembly's root frame, and the base geometry attaches *to* it via a joint exactly as the column and arms do. Includes are **relative** (`filename="base.xacro"`), not `$(find robot_description)`, so a source checkout and the installed tree expand identically. Install is `glob('urdf/*')` / `glob('meshes/*')`, never a hand-maintained list — D24's rule that a manual step the gate cannot see is the bug class, applied to packaging: adding a `.xacro` in PR3 must not also require remembering to register it. (`meshes/` therefore ships a real `README.md`, not a `.gitkeep`, because `glob()` skips dotfiles and the install directory would silently not exist.) The globs are **flat**, and this is a recorded limit rather than a claim of generality: `data_files` cannot copy a directory, so the first `meshes/<subdir>/x.stl` fails the *build* loudly (`can't copy …: doesn't exist or not a regular file`) — the invariant "you never register a file" holds for a flat directory, and PR2, which imports the first real mesh set, is where the `os.walk` version gets written against actual files instead of a guess at their layout.
  - **The gate resolves the description through the ament index, with no source-tree fallback.** `test/test_description.py` finds the file via `get_package_share_directory('robot_description')`, so the install wiring is part of what the gate verifies: a `.xacro` present in the source tree but missing from the install tree fails in CI instead of at bringup. A fallback to a `__file__`-relative path would mask precisely that break, so there is none — the price is that the suite requires a `colcon build` first, which `colcon test` (which puts the package's prefix on `AMENT_PREFIX_PATH`) always has.
  - **Four tools plus two wiring asserts, because each catches what the others cannot.** The `xacro` **CLI** expands (rc + stderr, and it is what a launch file actually runs); `check_urdf` parses the expansion; `urdf_parser_py` re-parses it and the link set is asserted **exactly** equal to `{base_link}`; every file the description *names* — `<mesh>` and `<texture>`, kept in a `FILE_BEARING_TAGS` constant rather than as a literal in the test — is resolved through the installed share tree and must exist. Alongside them, the top level must really `<xacro:include>` all three subassemblies, and the share layout must really be installed. Each line of that list is there because a perturbation proved the others miss it — the claims below were **executed**, including by a red-team pass that broke two of them: a *duplicate* link name is well-formed XML that only `check_urdf` rejects (the link *set* dedups it away); a **renamed** link (`base_link` → `base`) is valid URDF that only the exact-set assert catches, and that — not a "degenerate expansion", which `check_urdf` rejects perfectly well — is the set assert's real justification; a mesh *or texture* reference to a file that does not exist passes `check_urdf`, which validates the model but never opens either, so only the asset-resolution test sees it — and that test was itself re-broken once, catching `<mesh>` while `<texture>` sailed through, which is why the tag list is a named constant: "the gate knows about exactly one tag" is the bug, not the tag; deleting all three `<xacro:include>` lines leaves every other assert green while the arm silently leaves the robot; malformed XML fails the expansion; and dropping `urdf/*` from `data_files` fails everything. Two of those are assertions over an **empty** set (meshes) and a **fixed** set (includes) today — that is the point, the same bet as `EXPECTED_LINKS = {'base_link'}`: they cost nothing until PR2's first `.stl` and are load-bearing from that moment. Provisioning is part of the gate being real, not an afterthought: `check_urdf`'s binary reached the env only through the unpinned `ros-jazzy-desktop = "*"` closure until `ros-jazzy-urdfdom` was pinned explicitly. Later PRs extend `EXPECTED_LINKS` deliberately; a link set allowed to grow silently would stop being a gate. *Rationale:* geometry is the easy part to review and the hard part to notice regressions in — meshes especially, being the one part of a description a human reviewer cannot eyeball — so the gate has to check the things a reader cannot, and it has to be built *before* the geometry, because a harness added afterwards is a harness fitted to whatever already passes.

## 2026-08-13 — The test-count floor maintains itself

- **D28 — `scripts/test_baseline.json` is written by `pixi run test`, not by a human: the per-package floor ratchets UP automatically on any otherwise-green run, comes DOWN only when the run is explicitly told to (`ALLOW_TEST_DECREASE=1` / `--allow-decrease`), and counts the tests that **ran** rather than the tests that were collected.** The ratchet in `scripts/check_test_integrity.py` closes the gap `colcon test` leaves — a package that drops from 59 tests to 3 is still "green" — but it was only as current as the last person to remember `--update-baseline`, and nobody did: `robot_world` sat at a recorded floor of 50 while actually running 61, so eleven tests could have vanished with the guard reporting nothing. A guard whose calibration depends on a human step is a guard with a scheduled expiry date; this decision removes the step rather than documenting it harder (the same reading as D24 — *a manual step the gate cannot see is the bug class, not the instance*). Four clauses:
  - **Up is automatic, down is a gate — and that asymmetry is the whole design.** After the audit, a full run rewrites every entry where a package produced *more* than its floor, and creates an entry for a package that has none. Growth therefore carries its own bump in the same diff as the tests that caused it, and a stale floor cannot accumulate. What it must never become is "rewrite the floor to the current count", which is the obvious implementation and a rubber stamp: a package collapsing 61 → 3 would record 3 and pass, and the guard would be a very elaborate way of asserting that a number equals itself. So a count *below* the floor still fails, and re-cutting downwards needs `ALLOW_TEST_DECREASE=1` (or `--allow-decrease`) — one deliberate, greppable act, logged in the run output as `baseline <pkg>: 61 -> 3 (LOWERED)`. The environment variable is read permissively for yes (`1`/`true`/`yes`/`on`) and never for no, so `ALLOW_TEST_DECREASE=0` cannot lower a floor by being merely *set*.
  - **The floor counts tests that ran, so a skip is a deletion.** `@pytest.mark.skip` on ten tests removes exactly as much evidence about the code as deleting them, and it used to be invisible: the ten were still *collected*, so the recorded count was still cleared, and only the blunt all-skipped-package rule would ever have fired. `parse_xunit` now discounts any `<testcase>` carrying a `<skipped>` child (pytest's spelling for `skip`, `skipif`, `importorskip` **and** `xfail`, all of which mean "this body did not run"), and a result that lists no cases at all has its suite-level skip count subtracted instead. The baseline's units changed with it: an entry means *non-skipped, non-linter tests*, which is why every floor was re-cut in the same PR that introduced the rule rather than being migrated.
  - **Nothing is written from a run that is not otherwise green.** A floor is a claim about how much testing this workspace really does, so it may only be cut from a run that actually did it: any package with no result file, zero tests, an all-skipped suite, stale evidence, or implementation code with no real test freezes the *entire* file — including the packages that grew — and so does any error or failure in the results (an error during collection silently costs a module's worth of tests without any package looking hollow). The failing package has already failed the run on its own, so the automatic path stays quiet rather than adding a second complaint; only an explicit `--update-baseline` treats the refusal as its own error. The practical property this buys: a red `pixi run test` never leaves a rewritten `test_baseline.json` in the tree for someone to commit by accident.
  - **`--audit-only` stays read-only; only the run that produced the results may move the floor.** `pixi run test-audit` re-reads whatever XML is lying in `build/`, which is evidence about some earlier run rather than about the tree as it now stands — too weak a basis for a floor, and it would let a stale build directory quietly re-cut the file. It therefore never auto-bumps, and an `ALLOW_TEST_DECREASE` left exported in a shell does not even suppress the *report* of a shortfall there, because a permission the mode cannot act on must not become an exemption. `--update-baseline` still works in that mode — it is now "allow a decrease, and also prune entries for packages this run did not cover", the explicit gesture for repairing the file after a package is renamed or removed, since the automatic path cannot tell a package that left from one that broke.
  - *Rationale:* the ratchet's value is entirely in its calibration, and the previous design put that calibration on the one part of the loop that has no gate — human memory. Automating the safe direction and gating the unsafe one keeps every guarantee the guard had (missing result, zero tests, all-skipped, below-floor, code-without-real-tests all still fail) while removing the only step that could rot. Recorded in the same PR that re-cut the drifted floors, so the committed numbers and the rule that maintains them landed together.

## 2026-08-13 — The base is authored from LeKiwi's numbers, not copied from its files (amends D27's PR2 mesh bullet)

- **D29 — The mobile base is a *parametric* 3-omniwheel holonomic base built from LeKiwi's names, joint types, two dimensions and its mount convention, with primitive geometry and no vendored meshes; the mount mapping (60°/180°/300°) and the outward-radial spin axis are verified numerically, `base_footprint` is a fixed *child* of `base_link`, and D27's flat-glob `os.walk` rewrite therefore moves to the first PR that actually lands meshes (closes #65, PR2 of the URDF/MJCF roadmap).** D26 picked the LeKiwi base and D27 built the harness to gate it; this decision is what filling `urdf/base.xacro` actually turned out to require, and it contradicts the roadmap's §PR2 expectation in one place (meshes) on evidence rather than taste. Six clauses, the last of which is a lesson rather than a decision:
  - **Cribbed as facts, not as files — because the upstream file is a CAD export.** `SIGRobotics-UIUC/LeKiwi`'s `URDF/LeKiwi.urdf` (Apache-2.0) is a raw export: 16-digit float origins, no parameters, and a `drive_motor_mount → ST3215_Servo_Motor → omni_wheel_mount` chain of intermediate links per wheel that is a modelling artifact rather than kinematics. Copying it would put six fixed links into TF, into `EXPECTED_LINKS` and into PR7's MJCF for zero information. What is taken instead is: the three joint names **`base_left_wheel`, `base_back_wheel`, `base_right_wheel`** and their `continuous` type (upstream's `URDF/JOINT_NAMES.md` records that these were deliberately renamed to match the LeRobot driver's motor keys, so joint-state and command dictionaries are directly comparable between driver and URDF — D26's single-ecosystem rule applied to naming, and the thing PR6 will cash in), and the two sourced dimensions `wheel_radius = 0.05` / `base_radius = 0.125` from `huggingface/lerobot`'s `lekiwi.py`. **`base_radius` is the *driver's* number, and upstream's own mechanics disagree with it** — resolving LeKiwi's URDF through its CAD link chain puts its three wheels at radii 0.0992 / 0.1192 / 0.1000 m, i.e. not even on a common circle, none of them 0.125. Following the driver is nonetheless right, and is the whole point: the driver is the contract PR6 cashes in, so the URDF must agree with *it* rather than with the CAD. Recorded because PR6/PR7 will meet the discrepancy and should not treat it as a bug in this model. Every other dimension is an `<xacro:property>` marked **ESTIMATED** in the file itself rather than given a citation it does not have, and the inertias are *computed* from those same properties by the solid-cylinder formulas so a retuned dimension cannot leave a stale tensor behind. Attribution is a header comment naming each source, its license and which constant came from where; no `NOTICE`/`THIRD_PARTY` file, because no third-party file is vendored.
  - **The mount mapping is 60° / 180° / 300°, and the driver's `[240, 0, 120]` is a trap.** In the REP-103 body frame (x forward, y left, z up), `base_left_wheel` sits at 60° (front-left), `base_back_wheel` at 180° (rear centre), `base_right_wheel` at 300° (front-right). The LeRobot driver's `angles = np.radians(np.array([240, 0, 120]) - 90)` is the wheels' **rolling directions**, not their mount positions; the two differ, and reading the array as mount positions puts every wheel in the wrong place. Verified twice by execution, not recalled: with mount angle φ and rolling direction `d = ẑ × r̂ = (−sin φ, cos φ)`, the matrix `[[−sin φ, cos φ, base_radius]]` reproduces the driver's `m` exactly; and independently, resolving upstream LeKiwi's own wheel joints through its CAD link chain into its root frame puts them at 150.35° / 270.29° / 30.35°, i.e. exactly these three under the ~90° rotation between the CAD frame and REP-103. Each wheel's joint `<axis>` is written **`0 0 1` in a frame rotated by `rpy = (0, π/2, φ)`**, not as a radial vector with zero rpy: that makes the child link's +z the spin axis pointing radially outward (the conventional wheel-link frame, and what upstream uses — its axes resolve to the outward radial to 4 decimal places), and it is the *composition* that PR6 and PR7 depend on, which is why the gate asserts the rotated axis rather than the literal. One caveat recorded so PR6 does not inherit an over-claim: a positive joint velocity moves the wheel's **contact-patch material** along `+d̂`, which under the rolling constraint moves the **body** along `−d̂`, while the driver's positive wheel speed means the body moves along `+d̂`. Whether a physical Feetech motor's positive direction matches the URDF axis is a calibration fact, not a geometric one, and upstream carries the same relation; PR6/PR7 must confirm it in sim rather than assume either sign.
  - **`base_link` keeps no geometry, and `base_footprint` is its child — which constrains odometry.** D27 fixes `base_link` in the top-level file as the assembly's root frame, and xacro does not merge two `<link>`s of one name, so the issue's literal "`base_link` collision + visual geometry" is unbuildable. The base instead attaches **`base_chassis_link`** (the drive plate / Råskog-cart body, a primitive puck) to `base_link` with a fixed joint, exactly as the column and arms will. `base_footprint` is likewise a **fixed child** at `z = −wheel_radius`, not the root: the REP-120-shaped alternative would move the root-frame declaration out of the top level for a cosmetic gain. The consequence is load-bearing for a later PR, because a TF link has exactly one parent: whatever publishes odometry (PR6 / Nav2 bringup) **must publish `odom → base_link`, never `odom → base_footprint`**, or the tree breaks at runtime.
  - **Primitives, no meshes — so D27's `os.walk` rewrite moves to the first mesh-bearing PR.** Three reasons, all from the probe: the LeKiwi omniwheel STL is **15 MB** and its URDF references three copies, against a repo with no git-lfs and no asset-size policy; the only cheap upstream mesh is LeKiwi's flat *drive plate*, while per D26 our chassis is XLeRobot's IKEA-Råskog-cart frame — whose own URDF models the cart with box collisions and has **no wheel joints at all** — so vendoring it would assert geometry this robot does not have; and convex primitives are the *better* collision geometry for a mobile base anyway (what MoveIt/Nav2/MuJoCo want), with visual fidelity the only loss and the one thing sim-first does not need yet. This amends the roadmap's §PR2 bullet: `setup.py`'s flat globs and their recorded limit stay exactly as D27 left them, and the `os.walk` install belongs to the first PR that lands real meshes (likely PR4's SO-101 arm STLs) — written, as D27 asked, "against actual files rather than against a guess about their layout".
  - **The gate grew by seven — two of them the red-team's, and the two that matter most.** `EXPECTED_LINKS` becomes the six links of the base, and `test_description.py` adds: exactly three `continuous` wheel joints with those exact names, each driving the link named after it (a fourth wheel, a rename, a `revolute` retype or a cross-wiring are all invisible to a link-set assert); the wheels on one circle about `base_link` 120° apart with axes checked *after* rotation by their own rpy; **the LeRobot driver's body→wheel matrix, rebuilt from the parsed model and compared row-for-row to the driver's own constant**; `base_footprint` fixed under `base_link` at minus the wheel radius *read from the model's own wheel geometry*, so the two cannot drift; visual **and** collision geometry on every link that is a body, with the chassis's drawn and collided cylinders required to agree and its underside required to clear the wheels; a positive mass and positive `ixx/iyy/izz` on every link that is not a pure frame (a massless moving body is a valid URDF and an unusable MJCF); and the model **loading in `robot_state_publisher`**, which builds a KDL tree and so rejects models both parsers accept, and which is the first real consumer on the roadmap. That last one is passed a **params file**, not `--ros-args -p robot_description:=<xml>` — an override rule is parsed as a single-line YAML scalar, so a multi-line URDF aborts in rcl before the node sees it — and it is torn down by **process group**, because `ros2 run` re-spawns the node and signalling the wrapper alone leaves an orphan holding the pipe. The load-bearing clauses were each confirmed by perturbation — mis-spaced mounts, a flipped axis, a dangling child link, a zero wheel mass, a left/right wheel swap, a cyclic and a global mount rotation, a retuned wheel radius, a deleted `<visual>`, a deleted `<collision>`, a buried chassis, a displaced and a rotated chassis, a cross-wired joint — each failing exactly its own test with a legible message. That is a list, not a "**every** assertion": several narrower clauses (the parent-frame and axle-plane checks, the joint count and type, the degenerate-cylinder check) ship on argument rather than on a perturbation, and saying so is the point — a decision entry that rounds its own evidence up is the failure this PR already had to fix once.
  - **Relational assertions are not enough, and finding out cost a red-team round.** The base's layout was first gated entirely by comparing the wheels *to each other* — equal radii, 120° gaps, each axis radial at its own measured angle. Every one of those is invariant under rotating or permuting the mount set as a whole, so **swapping `base_left_wheel` with `base_right_wheel`, or shifting all three mounts cyclically by 120°, left the entire suite green** while the model disagreed with the driver about which motor sits where: solved against the driver's matrix, the swapped base drives *backward* on a forward command, and the shifted one drives 120° off. The mapping from motor key to body direction is **absolute, not relational**, and nothing asserted it. The fix is to assert the contract literally rather than a property of the layout — hence the driver-matrix row comparison above, which passes the shipped model to `1.8e-16` and fails all three permutations. The general lesson, worth more than the instance: *a gate built only from internal consistency checks certifies self-consistency, and a wrong model can be perfectly self-consistent.* Ask of each new geometric assertion whether it is relational or absolute, and make sure at least one absolute one pins the artifact to whatever outside contract it exists to satisfy. The same round found the base's collision and visual geometry entirely ungated (the issue's own first acceptance criterion: the chassis could lose both and stay green) and a real modelling bug behind it — the chassis puck's underside sat exactly on the axle plane, burying the top half of every wheel in the body solid, siblings under `base_link` so filtered by nothing. Both are now asserted, the clearance as a *relationship between numbers read off the model* rather than as the literal that satisfies it today. *Rationale:* the cheapest thing to get wrong here is a number nobody can eyeball — a wheel 90° from where the driver thinks it is produces a robot that drives sideways when told to drive forward, and passes every check D27 shipped. Authoring the base parametrically makes those numbers reviewable; asserting relationships between them keeps retuning cheap; and asserting the driver's matrix outright is what makes mis-mounting a test failure rather than a comment.

Twice a fix for the defect introduced a fresh instance of it, and the last two were authored by the reviewer enforcing the rule. The trap that caught it, worth stating because it is not obvious: **a finding labelled VERIFIED is verified for its own claim, not for the inference you draw from it.** The prompt was never the only ungated prose here, and this entry is the proof — it is the least-read, longest-lived prose in the repo, and it was the hardest single thing in this feature to make true.
